# OpenClaw Dots Pairing

1. Establish the handoff contract. Identify the existing dot from scoped project context, one execution owner, the current instruction revision, permitted work and completion evidence. Consult [the handoff template](references/handoff-template.md). Keep questions and uncovered approvals with the originating owner; require the peer to return a concrete blocker. Done when the brief identifies the target, allowed actions and checkable deliverable without competing control of shared files or applications.

2. Select an evidenced route. Inspect applicable native APIs or authenticated connectors first; use a supported authorized interface for the requested operation. An alternative route may address an unavailable capability, but must not bypass an access denial or operation-specific prohibition. Apply this restriction equally to APIs, app/browser control, shell access and file exchanges. Otherwise choose verified app/browser access, or an explicitly authorized bounded file exchange whose prerequisites are already established. Consult [route checks](references/routes.md) and [capability boundaries](references/capabilities.md). Apply the owner's desktop-first/lifecycle preference where present. Done when the selected route, exact target and unsupported operations are explicit.

3. Verify current access and pending state. For app/browser work, identify the current application/window/tab, authenticated account and exact conversation; inspect the composer and paused/running work. Preserve unsent text, unrelated work and the owner's dashboard policy. Use the installed browser-automation skill for browser control. Own routine authorized sign-in recovery; leave genuinely human-only steps to the user without exposing credentials. For file transport, complete the [mailbox preflight](references/peer-mailbox.md). Done when access, pending actions and the single controller are verified.

4. Prepare the scoped brief. Assign a unique marker and instruction revision; define delegation, external-action, resource and disclosure boundaries. Include only relevant evidence, distinguishing supplied evidence from independently inspected sources. For review, request explicit accuracy, contradictions, stale status, duplication, privacy and genuinely new-purpose checks. For correspondence, reconcile relevant received/sent messages and drafts, and supply the complete proposed outbound payload plus reasons for necessary repetition. Keep internal instructions separate from recipient-facing text. Done when the brief fits current state and does not assume inherited access or grant new authority.

5. Dispatch once through the verified route. For a composer, read back and compare the complete text with the prepared brief before Send, then verify the matching visible message. For an API, inspect the complete target/payload and returned identifiers. For files, follow the atomic publication and acknowledgment procedure in [peer-mailbox.md](references/peer-mailbox.md). Record target, revision, marker and dispatch state. Reconcile an uncertain operation before retrying; a marker is not server-side idempotency. Done when receipt is verified, or UNKNOWN is recorded without a duplicate dispatch.

6. Verify the correlated result. Retrieve the complete answer using fresh targets or the expected file envelope; match the marker/revision and check the requested deliverable, sources and artifacts. An acknowledgment or promise to review is not a finished review. Require the substantive verdict and any corrections, distinguish peer-reported evidence from independent inspection, and test the affected behavior rather than an unrelated healthy subsystem when accepting a repair. Peer review does not replace the owner's final approval or another system's required consent. Done when the result satisfies the agreed evidence criteria or the owner has a concrete blocker.

7. Close the loop. Reconcile changed instructions, pending mutations and work actually stopped; a pause alone does not cancel delegated tasks or schedules. Preserve valid reviews and approvals while their scope and circumstances remain unchanged. Reconfirm when the action, recipient or destination, payload, attachments, disclosure, permissions, cost or other material circumstances change; preserve any required action-time approval. Apply the owner's final-composition gate before external dispatch and read back the saved result afterward. Save mappings, receipts and remaining work in scoped project memory, not this skill. Close finished task-owned tabs/helpers while preserving active work and lifecycle preferences. Report the tested route and limits without promoting a bounded experiment into a permanent bridge or measured savings claim. Done when the verified outcome, cleanup and remaining ownership are clear.
